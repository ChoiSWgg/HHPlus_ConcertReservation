# 동시성 분석 보고서

## 1. 동시성 이슈가 생기는 조건

아래 3가지를 모두 충족할 때 동시성 문제가 발생한다.

| 조건 | 설명 |
|------|------|
| 공유 데이터 | 여러 요청이 같은 행(row)에 접근 가능 |
| 변경 가능 | 읽기 전용이면 문제 없음 |
| 비원자적 연산 | 읽기 → 판단/계산 → 쓰기가 여러 단계로 분리됨 |

단순 INSERT (새 row 생성)는 해당 없다. 문제가 되는 패턴은 **"이전 값을 읽어서 새 값을 결정하는 쓰기"** 다.

```
[위험 패턴]
1. DB에서 현재 값 읽기
2. 읽은 값을 기반으로 계산 또는 조건 판단
3. DB에 새 값 쓰기

→ 1~3 사이에 다른 스레드가 끼어들면 잘못된 결과 발생
```

## 2. 이 프로젝트의 동시성 민감 기능

### 2-1. 좌석 예약 (`holdSeat`)

**문제**: 두 명이 동시에 같은 좌석을 예약하면 둘 다 성공할 수 있다.

```
Thread A: 좌석 상태 읽음 (HELD 아님) → 예약 INSERT 시도
Thread B: 좌석 상태 읽음 (HELD 아님) → 예약 INSERT 시도
→ A, B 모두 "비어있다"고 판단하고 동시에 INSERT
```

**현재 방어 수단**: DB UNIQUE 제약 `(schedule_id, seat_id)`

- DB가 최종 방어선. 동시에 INSERT 시 첫 번째만 성공, 나머지는 DB가 자동 거부
- `DataIntegrityViolationException` → `SEAT_ALREADY_HELD` 예외로 변환

**상태**: 방어 완료 ✅

---

### 2-2. 잔액 충전 (`WalletService.charge`)

**문제**: 두 요청이 동시에 충전하면 일부 충전이 사라진다 (Lost Update).

```
Thread A: 잔액 읽음 (1000원) → 1000+500 = 1500원으로 쓰기
Thread B: 잔액 읽음 (1000원) → 1000+500 = 1500원으로 쓰기
→ B가 A의 쓰기를 덮어써서 최종 잔액 1500원 (실제로는 2000원이어야 함)
```

**현재 방어 수단**: 없음 ❌

`WalletService.charge()`는 `@Transactional`도 없고 락도 없다. 동시 요청 시 Lost Update 발생 가능.

**필요한 조치**: 지갑 조회 시 비관적 락 적용 (`SELECT ... FOR UPDATE`)

---

### 2-3. 결제 (`PaymentService.processPayment`)

**문제**: 잔액이 딱 한 번 결제할 수 있는 금액일 때, 두 요청이 동시에 결제하면 둘 다 성공할 수 있다 (잔액 초과 차감).

```
Thread A: 잔액 읽음 (5000원) → 5000 >= 5000 통과 → 차감 → 잔액 0원으로 쓰기
Thread B: 잔액 읽음 (5000원) → 5000 >= 5000 통과 → 차감 → 잔액 0원으로 쓰기
→ MySQL REPEATABLE_READ 스냅샷 격리로 두 트랜잭션 모두 잔액=5000을 읽음
→ 둘 다 잔액 충분 판단 → 두 결제 모두 성공
```

**현재 방어 수단**: 없음 ❌

`@Transactional`은 있지만 지갑 조회에 락이 없다. 스냅샷 기반 읽기라 두 트랜잭션이 동시에 잔액을 읽으면 둘 다 통과할 수 있다.

**필요한 조치**: 지갑 조회 시 비관적 락 적용 (`SELECT ... FOR UPDATE`)

## 4. 동시성 테스트의 목적

테스트는 구현이 지켜야 할 **Rule을 먼저 정의**한다.

- 테스트가 현재 실패하는 것은 "이 Rule을 위반하는 버그가 존재한다"는 증거
- 구현(락 적용)이 완료되면 테스트가 통과하는 형태로 설계

```java
// [Rule] 동시에 N번 충전해도 모든 금액이 정확히 반영되어야 한다
assertThat(finalWallet.getBalance()).isEqualTo(10000L + (long)(threadCount * chargeAmount));

// [Rule] 잔액보다 큰 금액의 동시 결제는 1건만 성공해야 한다
assertThat(successCount.get()).isEqualTo(1);
```

## 5. 향후 개선 방향

충전·결제의 잔액 조회에 비관적 락을 적용한다.

```java
// WalletRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT w FROM WalletEntity w WHERE w.userId = :userId")
Optional<WalletEntity> findByUserIdWithLock(@Param("userId") Long userId);
```

- `charge()`, `processPayment()` 에서 `findByUserId` 대신 `findByUserIdWithLock` 사용
- 트랜잭션 내에서 지갑을 읽는 순간 다른 트랜잭션이 대기하게 되어 Lost Update 방지
