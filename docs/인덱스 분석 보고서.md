# 인덱스 분석 보고서

## 1. 분석 목적

데이터가 증가했을 때 DB 조회 성능이 저하될 수 있는 쿼리를 사전에 파악하고,
인덱스 추가 또는 테이블 설계 개선을 통해 성능을 확보하기 위한 분석입니다.

---

## 2. 분석 대상 선정 기준

Repository의 `findBy~` 메서드를 기준으로 실제 사용되는 WHERE 조건 컬럼을 추출하고,
아래 3가지 기준으로 인덱스 필요 여부를 판단했습니다.

1. **조회 빈도**: 해당 쿼리가 얼마나 자주 실행되는가
2. **데이터 증가 가능성**: 데이터가 쌓일수록 풀스캔 비용이 커지는 테이블인가
3. **카디널리티**: WHERE 조건 컬럼의 값이 얼마나 다양한가 (값이 다양할수록 인덱스 효과 큼)

---

## 3. 쿼리별 분석

### 3-1. `reservations` — 예약 중복 확인

```sql
-- ReservationJpaRepository.findByScheduleIdAndSeatId
SELECT * FROM reservations WHERE schedule_id = ? AND seat_id = ?
```

| 항목 | 내용 |
|------|------|
| 실행 시점 | 좌석 예약 요청마다 실행 |
| 조회 빈도 | 높음 |
| 데이터 증가 가능성 | 높음 (예약 건수에 비례) |
| 카디널리티 | 높음 (스케줄 × 좌석 조합) |
| 현재 인덱스 | `UNIQUE(schedule_id, seat_id)` 이미 존재 |

**결론**: 추가 인덱스 불필요. UNIQUE 제약이 자동으로 복합 인덱스를 생성하므로 해당 쿼리는 인덱스 스캔으로 동작합니다.

---

### 3-2. `reservations` — 스케줄별 예약 목록 조회

```sql
-- ReservationJpaRepository.findAllByScheduleId
SELECT * FROM reservations WHERE schedule_id = ?
```

| 항목 | 내용 |
|------|------|
| 실행 시점 | 특정 스케줄의 예약 현황 조회 시 |
| 조회 빈도 | 중간 |
| 데이터 증가 가능성 | 높음 |
| 카디널리티 | 높음 |
| 현재 인덱스 | 별도 없음 |

**분석**: `UNIQUE(schedule_id, seat_id)` 복합 인덱스의 **선두 컬럼이 `schedule_id`** 이므로,
`WHERE schedule_id = ?` 단독 조건도 해당 복합 인덱스를 활용할 수 있습니다.
MySQL은 복합 인덱스에서 왼쪽부터 순서대로 컬럼을 활용하는 **좌측 접두사(Leftmost Prefix)** 규칙을 따르기 때문입니다.

**결론**: 추가 인덱스 불필요. 기존 복합 인덱스로 커버됩니다.

---

### 3-3. `concert_schedules` — 콘서트별 스케줄 조회

```sql
-- ConcertScheduleJpaRepository.findByConcertId
SELECT * FROM concert_schedules WHERE concert_id = ?
```

| 항목 | 내용 |
|------|------|
| 실행 시점 | 콘서트 스케줄 목록 조회 시 |
| 조회 빈도 | 높음 (유저가 예약 전 반드시 조회) |
| 데이터 증가 가능성 | 높음 (콘서트 회차 누적) |
| 카디널리티 | 높음 (콘서트 수만큼 다양) |
| 현재 인덱스 | 없음 → 풀스캔 발생 |

**결론**: 인덱스 추가 필요

```sql
CREATE INDEX idx_concert_schedules_concert_id ON concert_schedules (concert_id);
```

---

### 3-4. `wallets` — 유저별 지갑 조회

```sql
-- WalletJpaRepository.findByUserId
SELECT * FROM wallets WHERE user_id = ?
```

| 항목 | 내용 |
|------|------|
| 실행 시점 | 결제 시 잔액 확인, 잔액 충전 시 |
| 조회 빈도 | 높음 (결제마다 실행) |
| 데이터 증가 가능성 | 높음 (유저 수에 비례) |
| 카디널리티 | 높음 (유저 수만큼 다양) |
| 현재 인덱스 | 없음 → 풀스캔 발생 |

**참고**: `wallets`는 `users`와 1:1 공유 PK 구조이므로 `user_id = id`가 항상 성립합니다.
따라서 `findByUserId`는 사실상 PK 조회와 동일하며, `UNIQUE` 인덱스를 추가하면 충분합니다.

**결론**: UNIQUE 인덱스 추가 권장

```sql
CREATE UNIQUE INDEX idx_wallets_user_id ON wallets (user_id);
```

---

### 3-5. `payments`, `seats`, `concerts` — PK 조회만 사용

```sql
-- findById (PK 조회)
SELECT * FROM payments WHERE id = ?
SELECT * FROM seats WHERE id = ?
SELECT * FROM concerts WHERE id = ?
```

PK는 기본적으로 클러스터드 인덱스로 관리됩니다.
추가 인덱스 없이도 O(log N)으로 조회되므로 인덱스 추가가 불필요합니다.

## 4. 인덱스 설계 요약

| 테이블 | 컬럼 | 인덱스 종류 | 조치 |
|--------|------|------------|------|
| `reservations` | `(schedule_id, seat_id)` | UNIQUE | ✅ 이미 존재 |
| `concert_schedules` | `concert_id` | 일반 인덱스 | ➕ 추가 필요 |
| `wallets` | `user_id` | UNIQUE 인덱스 | ➕ 추가 필요 |
| `payments` | `id` | PK (기본) | ✅ 추가 불필요 |
| `seats` | `id` | PK (기본) | ✅ 추가 불필요 |
| `concerts` | `id` | PK (기본) | ✅ 추가 불필요 |

---

## 5. 인덱스 추가 시 트레이드오프

인덱스는 읽기 성능을 높이지만 쓰기 성능을 낮춥니다.

| 항목 | 인덱스 있을 때 | 인덱스 없을 때 |
|------|-------------|-------------|
| SELECT | 빠름 (인덱스 스캔) | 느림 (풀스캔) |
| INSERT / UPDATE / DELETE | 인덱스도 함께 갱신 → 쓰기 비용 증가 | 쓰기 비용 낮음 |
| 저장 공간 | 추가 공간 사용 | 없음 |

**이 프로젝트에서의 판단**:
- `concert_schedules`: 조회가 쓰기보다 압도적으로 많으므로 인덱스 추가 이득이 큼
- `wallets`: 결제마다 읽기가 발생하고 쓰기(충전/차감)는 상대적으로 적으므로 인덱스 추가 이득이 큼

## 6. Entity 반영 방법

JPA에서는 `@Table` 어노테이션의 `indexes` 속성으로 인덱스를 선언합니다.

**`ConcertScheduleEntity`**
```java
@Table(name = "concert_schedules",
    indexes = @Index(name = "idx_concert_schedules_concert_id", columnList = "concert_id"))
```

**`WalletEntity`**
```java
@Table(name = "wallets",
    indexes = @Index(name = "idx_wallets_user_id", columnList = "user_id", unique = true))
```
