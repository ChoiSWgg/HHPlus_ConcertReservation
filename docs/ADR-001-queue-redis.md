# ADR-001: 대기열 구현 방식 — Redis 선택

## 상태
결정됨

## 배경

콘서트 예약 시스템에서 많은 유저가 동시에 진입할 때 순서를 보장해야 한다.
대기열 구현 방식으로 **Redis** 또는 **DB** 두 가지를 검토했다.

## 선택지 비교

| 항목 | Redis (ZSet) | DB (테이블) |
|------|-------------|------------|
| 순서 저장 | 점수(timestamp) 기반으로 자동 정렬 | 별도 ORDER BY + 인덱스 필요 |
| 동시 접근 | 한 번에 한 명씩 처리 (충돌 없음) | 여러 명이 동시에 쓸 때 락 필요 |
| 순위 조회 | 바로 읽기 가능 | DB 읽기 후 계산 |
| 데이터 유지 | 서버 재시작 시 사라짐 | 영구 보존 |
| 구현 복잡도 | 낮음 | 높음 (만료 처리, 인덱스 등) |

## 결정

**Redis ZSet** 을 사용한다.

- 유저 진입 시: `ZADD queue:waiting {timestamp} {userId}` 로 순서 저장
- 순위 조회 시: `ZRANK` 로 몇 번째인지 읽기
- 순위 100 미만이면 `ACTIVE`, 이상이면 `WAIT` 상태 반환
- 결제 완료 시: `ZREM` 으로 대기열에서 제거

## 이유

대기열에서 중요한 건 두 가지다.

1. **빠른 순위 읽기**: Redis는 ZSet에 넣는 순간 자동 정렬되어 별도 계산 없이 바로 읽을 수 있다.
2. **동시 접근 안전성**: Redis는 한 번에 한 명씩 명령을 처리하므로, 여러 명이 동시에 진입해도 순서가 꼬이지 않는다.

DB를 쓰면 동시에 여러 명이 쓸 때 충돌을 막기 위한 락 처리가 필요하고 구현이 복잡해진다.

대기열은 일시적인 상태라 서버 재시작 시 사라져도 유저가 다시 진입하면 되므로, 영속성 부재는 허용 가능한 트레이드오프다.

## 결과

- 토큰은 별도 `queue:token:{userId}` 키에 문자열로 저장
- `QueueRedisRepository` 가 ZSet(순위) + String(토큰) 두 자료구조를 함께 관리
- 대기열 제거는 `PaymentFacade` 에서 결제 완료 후 호출 (도메인 간 결합 방지)
