# 테스트 전략

## 단위 테스트 vs 통합 테스트

| 구분 | 단위 테스트 | 통합 테스트 |
|------|------------|------------|
| 범위 | 클래스 1개 | 전체 흐름 (Controller ~ DB/Redis) |
| 외부 의존성 | 가짜(Mock)로 대체 | 실제 DB/Redis 컨테이너 사용 |
| 목적 | 비즈니스 로직이 맞는지 | 레이어들이 실제로 연결됐을 때 맞는지 |
| 속도 | 빠름 | 느림 (컨테이너 시작 시간 포함) |

## 통합 테스트를 쓰는 기준

**가짜(Mock)로는 잡을 수 없고, 실제 DB/Redis가 있어야 발견되는 문제**에만 쓴다.

- JPA 쿼리가 실제 DB에서 맞는지
- DB 쓰기/읽기 순서(트랜잭션)가 맞는지
- Redis 명령이 실제로 동작하는지
- 여러 도메인을 가로지르는 흐름이 연결되는지
- 여러 명이 동시에 DB에 쓸 때 제약이 맞게 동작하는지

## 통합 테스트 목록

### 주요기능

| # | 테스트 | 선정 이유 |
|---|--------|----------|
| 1 | 전체 플로우 (토큰발급 → 예약 → 결제) | 핵심 흐름, 3개 도메인 DB 연결 검증 |
| 2 | 만료 후 같은 좌석 재예약 성공 | UNIQUE 제약 + rehold 패턴이 실제 DB에서 동작하는지 |
| 3 | 동시 예약 → 1명만 성공 | 여러 명이 동시에 DB에 쓸 때 1명만 성공하는지 |

### 예외/경계 케이스

| # | 테스트 | 선정 이유 |
|---|--------|----------|
| 4 | 잔액 부족 시 결제 실패 | 실패 시 DB 쓰기가 취소(롤백)되는지 |
| 5 | HELD 상태 좌석 중복 예약 실패 | 실제 DB에서 읽은 상태로 분기 검증 |
| 6 | 결제 완료 후 대기열 제거 확인 | DB 쓰기(결제) + Redis 삭제(대기열)가 함께 동작하는지 |
| 7 | 토큰 발급 → 순위 조회 | Redis에 실제로 쓰고 읽는지 |

### 단순 조회를 통합 테스트에서 제외한 이유

콘서트/스케줄/좌석 목록 조회처럼 단순히 DB에서 읽기만 하는 기능은
JPA가 보장하고 별도 비즈니스 로직이 없다.
통합 테스트는 컨테이너 실행, 속도, 유지보수 비용이 크기 때문에
얻는 가치보다 비용이 크면 쓰지 않는다.

## 테스트 환경

- Testcontainers: MySQL 8.0, Redis 7-alpine
- `AbstractIntegrationTest` 상속으로 컨테이너 공유 (테스트마다 재시작 방지)
- `spring.jpa.hibernate.ddl-auto=create-drop` 으로 테스트 실행마다 DB 스키마 초기화
